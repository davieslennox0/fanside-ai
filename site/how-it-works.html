How Fanside answers a question

Every request runs the same real pipeline — nothing here is precomputed or mocked.

  1. 1. Classify complexity

    Before anything runs, the question text is scored into one of three tiers — single-subgraph, multi-field, or multi-subgraph composition — and priced accordingly.

  2. 2. x402 payment challenge

    The API responds 402 Payment Required with the tier's price. The caller signs an EIP-3009 (or Permit2) USDC authorization and retries with the payment header — no on-chain approval transaction needed up front.

  3. 3. Self-hosted verify & settle on Base

    Fanside's own server verifies the signature and broadcasts the settlement itself — chain ID 8453/84532, USDC — using @x402/evm's ExactEvmScheme facilitator. No external facilitator service sits in the middle.

  4. 4. Search The Graph's Subgraph MCP

    Once payment settles, Fanside calls the live Subgraph MCP (subgraphs.mcp.thegraph.com): keyword search, a mandatory 30-day query-count check to pick the actively-used deployment, then fetches its real GraphQL schema.

  5. 5. Generate & execute a real query

    An LLM call turns the question plus the subgraph's schema into a GraphQL query restricted to that schema's actual fields — then it's executed live against the subgraph.

  6. 6. Synthesize the answer

    A second LLM call turns the raw JSON result into a plain-language answer grounded only in that data — never invented figures.

For agents & apps: /api/agent/query

Fanside is built to be called by other agents, not just humans in a chat UI. The agent-facing endpoint takes the same request shape and returns structured data (not prose-only) so a calling agent can parse subgraphs used and raw results, not just the summary. 

POST /api/agent/query
Content-Type: application/json

{ "question": "Compare Uniswap and Aave activity this week" }

→ 402 Payment Required (first call — no payment header yet)
{
  "x402Version": 2,
  "accepts": [{ "scheme": "exact", "network": "eip155:84532", "asset": "USDC", "maxAmountRequired": "100000", ... }]
}

→ retry with X-PAYMENT header containing the signed authorization

→ 200 OK
{
  "answer": "Over the past week, Uniswap saw ... while Aave ...",
  "tier": "composition",
  "price_usdc": "0.10",
  "subgraphs_used": [
    { "name": "Uniswap V3", "id": "..." },
    { "name": "Aave V3",   "id": "..." }
  ],
  "raw_results": [ { "subgraph": "Uniswap V3", "query": "...", "result": { ... } }, ... ]
}

Any x402-aware HTTP client (the reference x402-fetch/@x402/fetch wrapper, or a hand-rolled signer) can drive this loop — this is the same protocol used for the human-facing /api/ask, just with a response shaped for machine consumption.

Why The Graph is load-bearing here

Fanside has no local index and no cache of subgraph data — every answer requires a live MCP round trip (search → query-count check → schema → execute) at request time. Remove the MCP call and there is no product: the pricing tiers exist specifically to reflect how much real subgraph querying a question requires.
